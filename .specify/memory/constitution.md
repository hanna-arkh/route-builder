# Route Builder Constitution

## Core Principles

### I. Клиентская разработка и неизменяемый бэкенд

Route Builder — мобильное приложение для курьерского депо на React Native (Expo)
с TypeScript. Разработка MUST ограничиваться клиентом. Бэкенд `server.js` MUST
рассматриваться как черный ящик, запускаться локально и оставаться неизменным.
Запрещено изменять сервер для удобства клиента или прохождения клиентских проверок.
Клиент MUST адаптироваться к существующему контракту сервера. Это сохраняет
совместимость с предоставленным бэкендом.

### II. Реальное поведение сервера как источник истины

При любом расхождении между `API.md` и фактическим поведением `server.js`
абсолютный приоритет MUST иметь поведение реально запущенного сервера.
API-клиент и проверки интеграции MUST учитывать наблюдаемые форматы запросов,
ответов и ошибок. Расхождения MUST фиксироваться в материалах интеграции
с примером запроса и фактического ответа, без изменения сервера.
Если сервер недоступен, предположения MUST явно обозначаться; соответствие
интеграции реальному серверу нельзя объявлять подтвержденным по документации
или мокам. Это предотвращает реализацию по недостоверному описанию API.

### III. Разделение ответственности и расширяемость

Код MUST разделяться на UI-компоненты, API-клиент и слой управления состоянием.
UI MUST отображать данные и передавать пользовательские действия; сетевые запросы
и преобразование ответов MUST находиться в API-клиенте; состояние операций
и координация сценариев MUST находиться в слое управления состоянием.
UI MUST NOT выполнять сетевые запросы напрямую. Контракты между слоями MUST
иметь типы TypeScript. Новый экран MUST добавляться через существующие границы
слоев без переноса сетевой логики в UI и переписывания несвязанных экранов.
Абстракции MUST иметь конкретную ответственность; отдельная библиотека управления
состоянием не обязательна. Это делает расширение приложения предсказуемым.

### IV. UX диспетчера и надежность операций

Основной сценарий — диспетчер, работающий стоя, в спешке, одной рукой.
Основные действия MUST быть доступны для такого использования; элементы управления
MUST иметь достаточную область нажатия и явную обратную связь. Экраны с загрузкой
данных MUST явно обрабатывать загрузку, ошибку и пустой список. Ошибка MUST
сообщать о результате операции и доступном следующем действии.

Создание маршрута MUST иметь защиту от повторных нажатий: с момента запуска
операции до ее завершения повторное действие MUST NOT отправлять второй запрос.
Защита MUST действовать в обработчике или слое состояния; кнопка MUST показывать
занятость и быть недоступна на время операции. После ошибки повторная попытка
MUST становиться доступной. При неизвестном результате запроса клиент MUST явно
сообщать об этом, не заявляя об успехе и не повторяя создание автоматически.

До отправки запроса создания маршрута клиент MUST проверять заполненность
инструкций для каждой остановки. Отсутствующее значение, пустая строка и строка
из пробелов MUST считаться незаполненными. При нарушении запрос MUST блокироваться,
а UI MUST указывать остановки, требующие исправления, сохраняя введенные данные.
Эти правила уменьшают риск дублей и неполных маршрутов в условиях спешки.

## Технологические ограничения

- React Native, Expo и TypeScript MUST оставаться основой клиента; изменения MUST
  учитывать производительность мобильных устройств и совместимость iOS и Android.
- Перед изменением кода, использующего Expo или React Native API, MUST
  определяться основная версия `expo` из `package.json` и читаться соответствующая
  документация `https://docs.expo.dev/versions/v<major>.0.0/`. Для остальных вопросов
  Expo MUST использоваться `https://docs.expo.dev/llms.txt` и указанные там страницы.
- Навигация MAY использовать базовое состояние в `App.tsx` либо простой стек
  навигации. Expo Router и файловая структура `src/app/` не обязательны.
  Выбранный подход MUST сохранять разделение UI, API-клиента и состояния
  и позволять добавлять экраны без переписывания несвязанных частей приложения.
- Зависимости MUST устанавливаться через `npx expo install`; при наличии `bun.lock`
  MUST использоваться `bunx expo install`. Перед добавлением зависимостей MUST
  проверяться доступные skills; предпочтение MUST отдаваться рекомендованным Expo
  модулям, если они удовлетворяют требованиям.
- Если `ios/` и `android/` отсутствуют, нативная конфигурация MUST задаваться через
  конфигурацию Expo и config plugins; создавать эти каталоги вручную запрещено.
  Добавление нативного модуля вне состава Expo Go MUST сопровождаться development build.

## Рабочий процесс и контроль качества

- Спецификации, планы и задачи MUST проверяться на соответствие четырем принципам
  до реализации; результаты MUST отражаться в соответствующем артефакте.
- Перед объявлением задачи завершенной MUST запускаться `npx expo lint` и
  `npx tsc --noEmit` (с `bunx` вместо `npx` при наличии `bun.lock`). Невозможность
  выполнения или ошибки MUST явно сообщаться; такие проверки нельзя считать пройденными.
- При изменении создания маршрута проверки MUST покрывать быстрые повторные
  нажатия, ошибку запроса, восстановление доступности действия и валидацию
  инструкций всех остановок, включая строки из пробелов.
- При изменении экранов с данными MUST проверяться загрузка, ошибка и пустой список;
  затронутые основные действия MUST проверяться на удобство использования одной рукой.
- Изменения интеграции MUST проверяться с локальным неизмененным `server.js`.
  Моки допустимы для изолированных проверок, но не подтверждают реальный контракт.
- Ревью MUST проверять отсутствие изменений бэкенда, соблюдение границ слоев,
  совместимость платформ и доказательства выполнения применимых проверок.

## Governance

Эта конституция определяет обязательные принципы Route Builder. Спецификации,
планы, задачи и реализация MUST ей соответствовать. `AGENTS.md` содержит
операционные инструкции; противоречия MUST явно разрешаться до реализации
затронутого решения, без молчаливого обхода правил.

Поправка MUST включать причину, перечень затронутых правил, оценку влияния на
текущую реализацию и план приведения ее в соответствие, если он необходим.
Изменение MUST быть явно утверждено сопровождающим проекта, в том числе прямым
поручением обновить конституцию. Поправка MUST обновлять версию и дату изменения;
дата первоначального принятия сохраняется.

Версия MUST следовать SemVer: MAJOR — удаление или несовместимое переопределение
принципов либо правил управления; MINOR — новый принцип, раздел или существенное
расширение требований; PATCH — уточнения без изменения обязательств.
Каждое ревью MUST проверять соответствие применимым правилам; обнаруженные
нарушения MUST исправляться либо сопровождаться утвержденной поправкой до
признания работы соответствующей конституции.
