# Feature Specification: Route Builder — Stops и Instructions

**Feature Branch**: `main` (текущая ветка; новая ветка не создавалась)

**Created**: 2026-10-26

**Status**: Draft

**Contract review**: 2026-10-26 — `server.js`, `API.md` и `designs/RouteBuilder-Screens.html`.

**Input**: User description: «Мобильное приложение для диспетчера курьерского депо:
два экрана Stops и Instructions, английский интерфейс LTR, выбор остановок,
количество посылок, обязательные инструкции и надежное создание маршрута».

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Создать маршрут с одной остановкой (Priority: P1)

Диспетчер одной рукой выбирает получателя, задает количество посылок, вводит
инструкцию и получает подтверждение создания маршрута.

**Why this priority**: Это минимальный законченный рабочий сценарий приложения.

**Independent Test**: С доступным справочником выбрать одну точку, указать две
посылки, ввести инструкцию и завершить маршрут; проверить сохраненные данные
и единственное подтвержденное создание.

**Acceptance Scenarios**:

1. **Given** открыт Stops, **When** справочник загружен, **Then** видны алфавитные
   секции и строки с инициалами, именем, адресом и телефоном; активен One stop.
2. **Given** выбран One stop, **When** диспетчер выбирает другую точку,
   **Then** она заменяет предыдущую; в нижней панели один чип и Continue (1 stops).
3. **Given** открыта пилюля количества, **When** диспетчер меняет число через
   минус/плюс и нажимает Save, **Then** новое количество видно на остановке;
   закрытие без Save не меняет сохраненное значение.
4. **Given** выбрана точка, **When** нажат Continue, **Then** открыт Instructions
   с именем, адресом, полем инструкции, счетчиком символов и Clear all.
5. **Given** инструкция заполнена, **When** диспетчер нажимает Finish instructions
   и создание с последующими уведомлениями завершено,
   **Then** созданный маршрут сохранен с его идентификатором, уведомления по всем
   остановкам имеют статус sent и показан успех; повторное нажатие не создает маршрут снова.

### User Story 2 - Подготовить маршрут с несколькими остановками (Priority: P1)

Диспетчер собирает несколько уникальных остановок, проверяет инструкции каждой
и исправляет состав маршрута до отправки.

**Why this priority**: Основная ценность — подготовить полный маршрут без
пропущенных инструкций и случайных повторов остановок.

**Independent Test**: В Multi-stop route выбрать три точки, изменить количества,
заполнить инструкции, удалить одну точку и создать маршрут из оставшихся двух.

**Acceptance Scenarios**:

1. **Given** выбран Multi-stop route, **When** выбраны три разных получателя,
   **Then** нижняя панель содержит три чипа и Continue (3 stops); повторный выбор
   уже выбранной строки снимает выбор, а не добавляет дубль.
2. **Given** несколько выбранных точек, **When** открыт Instructions,
   **Then** каждой точке соответствует одна карточка в порядке выбора.
3. **Given** одна инструкция пуста или содержит только пробелы, **When** диспетчер
   пытается завершить маршрут, **Then** отправка не начинается; каждая проблемная
   карточка показывает ошибку, введенные данные остальных карточек сохранены.
4. **Given** в карточке есть текст, **When** нажат ее Clear all,
   **Then** очищается только инструкция этой карточки и ее счетчик становится 0.
5. **Given** три карточки, **When** одна точка удалена, **Then** остаются две;
   их инструкции и количества сохранены, удаленная точка не попадает в маршрут.
6. **Given** черновик с инструкциями, **When** диспетчер возвращается на Stops
   и снова открывает Instructions, **Then** выбор, количества и инструкции сохранены.
7. **Given** выбрано несколько точек, **When** включен One stop,
   **Then** остается первая выбранная точка с ее количеством и инструкцией;
   при возврате в Multi-stop route снятые точки не восстанавливаются автоматически.

### User Story 3 - Найти получателя и восстановиться после ошибки загрузки (Priority: P2)

Диспетчер ищет точку в справочнике и понимает разницу между отсутствием совпадений,
пустым справочником и ошибкой связи.

**Why this priority**: Поиск ускоряет работу с большим справочником, а явные
состояния предотвращают ошибочное восприятие сбоя как отсутствия адресов.

**Independent Test**: Найти известного получателя, выполнить поиск без совпадений,
очистить строку, затем воспроизвести ошибку загрузки и успешную повторную попытку.

**Acceptance Scenarios**:

1. **Given** открыт Stops, **When** введен поисковый текст, **Then** показаны
   результаты поиска сервиса, сгруппированные по первой букве имени.
2. **Given** совпадений нет, **When** поиск завершен успешно, **Then** видно
   английское сообщение об отсутствии результатов; выбранные точки сохранены.
3. **Given** активен поиск, **When** строка очищена, **Then** вновь доступен полный
   справочник; выбор и количества не сбрасываются.
4. **Given** поисковый текст быстро изменен, **When** старый результат приходит
   позже нового, **Then** список соответствует последнему тексту поиска.
5. **Given** справочник загружается или произошла ошибка, **When** показан Stops,
   **Then** видны соответственно индикатор загрузки или ошибка с Retry;
   после успешного Retry показываются данные без потери выбора. При 429/503
   повтор не выполняется раньше срока Retry-After.
6. **Given** справочник действительно пуст, **When** загрузка завершена,
   **Then** показано состояние пустого справочника, отличимое от ошибки поиска.

### User Story 4 - Безопасно завершить отправку и обработать сбой (Priority: P1)

Диспетчер видит состояние отправки, сохраняет работу при ошибке и не создает
дубликаты быстрыми повторными действиями.

**Why this priority**: Дубли маршрутов и потеря инструкций нарушают работу депо.

**Independent Test**: На заполненном черновике выполнить быстрые повторные нажатия,
воспроизвести отказ сервиса, повторить действие после подтвержденного отказа
и отдельно проверить потерю ответа с неизвестным результатом.

**Acceptance Scenarios**:

1. **Given** корректный черновик, **When** действие создания нажато десять раз
   подряд до завершения отправки, **Then** начинается одна операция создания,
   показан индикатор и повторное действие заблокировано.
2. **Given** идет отправка, **When** диспетчер пытается менять состав или текст,
   **Then** отправляемый маршрут не изменяется; редактирование и переход назад
   заблокированы до результата операции.
3. **Given** сервис явно отклонил создание, **When** показана ошибка,
   **Then** данные сохранены и доступна управляемая повторная попытка.
4. **Given** связь потеряна и результат неизвестен, **When** показана ошибка,
   **Then** нет ложного успеха и автоматического повтора; ручной повтор доступен
   с предупреждением о возможности уже созданного маршрута.
5. **Given** получено подтверждение создания, **When** диспетчер продолжает работу,
   **Then** видит подтверждение создания на Instructions; полный успех показан
   после sent для всех остановок. Новый маршрут начинается явным действием;
   сбой уведомления не приводит к повторному созданию маршрута.

### User Story 5 - Просмотреть фотографии и довести уведомления до результата (Priority: P2)

Диспетчер использует фотографии предыдущей доставки как контекст для инструкции.
После Finish instructions он видит результат уведомления водителя по каждой точке,
включая частичный отказ, и повторяет только неудачную отправку.

**Why this priority**: Макет обещает отправку инструкций водителю при завершении;
создание draft-маршрута само по себе этого не выполняет. Фотографии помогают
описать место доставки, но их медленная загрузка не должна останавливать работу.

**Independent Test**: Открыть карточки с нулем фотографий и с отсутствующим URL,
создать маршрут с stp_1002, получить failed при первом уведомлении и sent при
явном повторе; убедиться, что маршрут остается один, остальные sent не повторяются.

**Acceptance Scenarios**:

1. **Given** открыта карточка, **When** фотографии загружаются несколько секунд,
   **Then** виден локальный индикатор; ввод инструкции и Finish instructions доступны.
2. **Given** загружены фотографии, **When** массив пуст либо URL равен null или
   изображение не загрузилось, **Then** видны соответственно пустое состояние
   либо заглушка; интерфейс не падает, теги подписаны на английском.
3. **Given** маршрут создан с id, **When** выполняются уведомления, **Then** каждое
   относится к этому маршруту и своей остановке; HTTP 200 со status=failed
   показывает отказ этой точки, а не успех всего маршрута.
4. **Given** точка получила carrier_rejected, **When** диспетчер нажимает Retry,
   **Then** повторяется только ее уведомление с новым ключом попытки; создание
   маршрута и уже успешные уведомления не повторяются.
5. **Given** ответ уведомления потерян после возможной обработки, **When** диспетчер
   повторяет ту же попытку, **Then** используется тот же ключ; одновременные
   уведомления одной точки не запускаются. Для нового повтора подтвержденного
   failed создается новый ключ, поскольку старый возвращает сохраненный отказ.

### Edge Cases

- Ноль выбранных остановок: Continue недоступна; удаление последней карточки
  возвращает на Stops с пустым выбором, создание маршрута недоступно.
- Одна посылка: минус не позволяет уменьшить количество ниже 1; дробные,
  нулевые и отрицательные значения не допускаются. Числовой packages_max и его
  строковое представление задают одинаковый верхний предел; null означает
  отсутствие заданного максимума, а не ноль.
- При инструкции длиной 200 единиц UTF-16 счетчик показывает 200/200;
  ввод/вставка сверх лимита не принимается без явного сообщения. Emoji могут
  занимать две единицы; нельзя разрезать суррогатную пару. Ограничение защищает
  от молчаливой обрезки сервером до 200 вместо 250 в API.md и макете.
- При page_size=50 исходный справочник содержит 24 уникальные точки, хотя
  total=25, total_pages=0 и has_more=true; пустая следующая страница завершает
  загрузку. Для page_size=10 вторая страница повторяет границу первой и теряет
  stp_1019; дедупликация сама по себе не восстанавливает пропущенную точку.
- items=null при поиске означает отсутствие совпадений, как items=[];
  это не ошибка ответа. Метаданные не определяют пустоту списка.
- Поиск скрывает выбранную точку: она остается в черновике и нижней панели.
- Получатели с одинаковыми именами или адресами остаются разными точками,
  если имеют разные идентификаторы; одинаковый идентификатор не дублируется.
- Имя начинается с цифры/символа или отсутствует: секция #; для отсутствующего
  имени/телефона отображается английская заглушка без выдуманных контактных данных.
- Длинные имена, адреса и открытая клавиатура не перекрывают ввод, ошибки
  и основные действия; карточки и список доступны для прокрутки одной рукой.
- Некорректный или неожиданный ответ сервиса не вызывает падение и ложный успех;
  показана ошибка с сохранением черновика и учетом неизвестного результата создания.
- Clear all делает соответствующую инструкцию невалидной; удаление невалидной
  точки исключает ее из проверки, не меняя остальные карточки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Приложение MUST иметь два экрана, Stops и Instructions. Все надписи,
  подсказки, ошибки и подтверждения MUST быть на английском; направление интерфейса — LTR.
- **FR-002**: Stops MUST загружать полный доступный справочник, показывать состояния
  загрузки, ошибки с Retry и пустого справочника (US3.5–6).
- **FR-003**: Строка MUST содержать инициалы, имя, адрес и телефон. Список MUST
  сортироваться по имени и группироваться по первой букве без учета регистра;
  неалфавитные/отсутствующие имена относятся к # (US1.1, US3.1, Edge Cases).
- **FR-004**: Поиск MUST получать результаты от сервиса по введенному тексту,
  показывать отсутствие совпадений, игнорировать устаревшие результаты и при очистке
  возвращать полный справочник без сброса выбора (US3.1–4).
- **FR-005**: Stops MUST предоставлять One stop и Multi-stop route; первый режим
  допускает максимум одну точку, второй — несколько уникальных точек (US1.2, US2.1,7).
- **FR-006**: Каждая выбранная точка MUST иметь целое количество посылок от 1;
  пилюля количества MUST открывать селектор с минусом, числом, плюсом и Save;
  изменения применяются только по Save. Число не превышает нормализованный
  packages_max, если он задан (US1.3, Edge Cases).
- **FR-007**: Нижняя панель MUST содержать горизонтально прокручиваемые чипы
  выбранных адресов и Continue (N stops), где N — число уникальных остановок,
  а не сумма посылок; при N=0 переход недоступен (US1.2, US2.1).
- **FR-008**: Instructions MUST показывать карточку каждой выбранной точки с именем,
  адресом, полем инструкции, счетчиком N/200 и Clear all; лимит соответствует
  серверным 200 единицам UTF-16 без повреждения emoji (US1.4, US2.2,4, Edge Cases).
- **FR-009**: Clear all MUST очищать только текст своей карточки; удаление точки
  MUST удалять ее карточку и исключать из маршрута, сохраняя остальные данные (US2.4–5).
- **FR-010**: Черновик MUST сохранять выбор, количества и инструкции при переходах
  между двумя экранами, поиске, загрузке и ошибках в текущем сеансе (US2.6, US3, US4).
- **FR-011**: Создание MUST блокироваться при пустом составе или хотя бы одной
  отсутствующей, пустой либо пробельной инструкции. Каждая проблемная карточка MUST
  показывать свою ошибку, снимаемую после исправления (US2.3, Edge Cases).
- **FR-012**: Создаваемый маршрут MUST содержать каждую выбранную точку ровно один раз,
  ее количество посылок и соответствующую инструкцию; снятые точки исключаются (US1–2).
- **FR-013**: Во время создания MUST быть видны занятость и блокировка повторной
  отправки и редактирования; быстрые повторные нажатия MUST NOT начинать дополнительные
  операции создания (US4.1–2).
- **FR-014**: Ошибки связи, отказ сервиса и неожиданные ответы MUST сохранять черновик
  и давать понятное действие восстановления. При неизвестном результате MUST быть
  предупреждение о возможном создании; автоматическое повторное создание запрещено (US4.3–4).
- **FR-015**: Подтверждение создания MUST основываться на 201 с корректными id,
  stops и status=draft. Полный успех Finish instructions MUST означать sent
  для каждой выбранной точки; при частичном отказе MUST отображаться результаты
  отдельных точек. Созданный маршрут MUST NOT создаваться заново при повторе
  уведомления; новый маршрут начинается явным действием (US4.5, US5.3–5).
- **FR-016**: Основные действия MUST быть доступны одной рукой; интерактивные области
  MUST быть не меньше 44×44 логических единиц, с видимой обратной связью; клавиатура
  MUST NOT закрывать активное поле и доступ к основным действиям (Edge Cases, SC-001).
- **FR-017**: Поведение клиента MUST соответствовать фактическому поведению
  предоставленного неизмененного локального сервиса, включая реальные форматы ошибок;
  несоответствие документации MUST NOT исправляться изменением сервера (US4, Dependencies).

- **FR-018**: Справочник и поиск MUST загружаться с page_size=50 и дедупликацией
  по id; конец определяется пустым items либо отсутствием новых id, а не total,
  total_pages или has_more. Ошибка страницы MUST NOT считаться концом загрузки;
  повтор сохраняет уже полученные точки (US3, Edge Cases, Service Contract).
- **FR-019**: Ошибки 429/503 с Retry-After MUST задавать минимальную паузу перед
  повтором; на время ожидания Retry недоступна с понятным английским сообщением.
  Ошибки 400/422 MUST NOT повторяться без исправления; поля fields MUST
  сопоставляться соответствующим данным, если возможно (US3.5, US4.3).
- **FR-020**: Карточки MUST показывать фотографии прошлой доставки с локальными
  состояниями загрузки/ошибки/пустоты, заглушкой для null/неработающего URL
  и английскими подписями тегов. Фотографии MUST NOT блокировать ввод или
  завершение маршрута (US5.1–2).
- **FR-021**: После создания MUST выполняться отдельное уведомление каждой
  остановки. Успех определяется status=sent, а не только HTTP 200. Ключ попытки
  MUST сохраняться при неизвестном результате и меняться при явном повторе
  подтвержденного failed; для одной точки допускается только одна активная
  попытка. Уже sent и POST создания MUST NOT повторяться; до завершения
  уведомлений состав и инструкции созданного маршрута не редактируются (US5.3–5).

### Key Entities *(include if feature involves data)*

- **Остановка справочника**: Уникальный идентификатор, имя получателя, адрес, телефон;
  zone, packages_max (число, числовая строка или null), last_delivery_at
  (ISO с Z, ISO без зоны либо Unix-секунды), необязательный notes=null;
  инициалы и алфавитная секция определяются для отображения. Телефон остается
  исходной строкой; null и отсутствующие необязательные поля допустимы.
- **Остановка черновика**: Ссылка на уникальную точку, количество посылок, инструкция,
  положение в порядке выбора, ошибки заполнения.
- **Черновик маршрута**: Режим выбора и упорядоченный набор выбранных остановок;
  сохраняется в пределах текущего сеанса и имеет состояние подготовки/отправки/ошибки/успеха.
- **Результат создания**: Подтвержденное создание, подтвержденный отказ или неизвестный
  результат; подтвержденный ответ содержит id маршрута, сохраненные stops и status=draft.
- **Фотография**: id, url (строка либо null), tag, width, height; принадлежит остановке.
- **Уведомление остановки**: id маршрута, stop_id, ключ попытки, status=sent/failed,
  reason при отказе, attempts, sent_at и deliveries при sent. Счетчик deliveries
  в этом сервере равен числу попыток, включая предыдущий отказ; он не доказывает
  количество реально успешных доставок уведомления.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Не менее 4 из 5 участников, представляющих диспетчера, с первой попытки
  создают маршрут из трех заранее заданных точек с короткими инструкциями за 3 минуты,
  работая стоя одной рукой, без помощи наблюдателя; время ожидания сервиса исключается.
- **SC-002**: Во всех проверках пустых/пробельных инструкций по каждой позиции
  трехточечного маршрута отправка блокируется, а все проблемные карточки отмечаются;
  после исправления ошибок маршрут можно завершить.
- **SC-003**: В 20 проверках десяти быстрых нажатий во время одной отправки
  возникает ровно одна операция создания и не более одного созданного маршрута.
- **SC-004**: Во всех сценариях подтвержденного отказа введенные инструкции,
  количества и выбранные точки сохраняются; успешный ручной повтор не требует повторного ввода.
- **SC-005**: В проверках поиска с обратным порядком получения результатов список
  всегда соответствует последнему запросу; очистка поиска всегда восстанавливает
  справочник и сохраняет весь выбор.
- **SC-006**: Все видимые состояния двух экранов, включая ошибки, пустые состояния
  и успех, используют английские надписи и направление LTR.
- **SC-007**: Подтвержденный успех всегда соответствует фактически созданному маршруту
  с теми же уникальными остановками, количествами и инструкциями во всех приемочных сценариях.

- **SC-008**: При загрузке исходного справочника доступны все 24 уникальные точки,
  включая 24/7 Pharmacy; дублей нет и загрузка завершается, несмотря на неверные
  метаданные. Поиск без совпадений всегда дает корректное пустое состояние.
- **SC-009**: Во всех проверках 200/201 единиц текста и emoji сохраненная инструкция
  совпадает с принятой пользователем; скрытая потеря текста отсутствует. Числовой
  и строковый максимум одинаково ограничивают количество, null не блокирует выбор.
- **SC-010**: При частичном отказе уведомлений повтор затрагивает только неуспешные
  точки, число созданных маршрутов остается равным одному, полный успех не показан
  до подтвержденной отправки всех уведомлений.

## Assumptions

- По умолчанию активен One stop; количество посылок — 1. Повторное нажатие выбранной
  строки снимает выбор. Переход из Multi-stop route в One stop сохраняет первую
  выбранную точку; порядок маршрута соответствует порядку выбора без оптимизации.
- Clear all относится к инструкции одной карточки. Счетчик учитывает пробелы
  и использует серверную меру длины UTF-16; корректность заполнения проверяется
  после исключения краевых пробелов, без молчаливого изменения текста инструкции.
- packages_max=null означает отсутствие заданного верхнего предела: API.md не
  задает для null значение по умолчанию. Клиент не придумывает общий лимит.
- Успех отображается в Instructions, новый маршрут возвращает на Stops с пустым
  черновиком. Отдельный третий экран не требуется. На кнопке сохранена заданная форма
  Continue (N stops), включая N=1.
- Восстановление после перезапуска приложения, офлайн-очередь, авторизация, карты,
  оптимизация маршрутов и история маршрутов не входят в текущую функцию.

### Dependencies and Scope Boundaries

- Источники: [server.js](../../server.js), [API.md](../../API.md),
  [макет экранов](../../designs/RouteBuilder-Screens.html). При конфликте контрактов
  абсолютный приоритет имеет server.js; бэкенд не изменяется.
- Сервис запускается локально, по умолчанию на порту 4000, без аутентификации.
  Адрес для устройства/эмулятора задается по API.md, а не всегда localhost.
- Макет задает Stops, Instructions, селектор количества, чипы, удаление точки,
  клавиатуру и фотографии. Примерные имена, количества, суммарные значения
  и неправильные буквенные секции не являются данными справочника.
- Ручной ввод адреса и Photo of the drop-off point в макете не имеют серверных
  эндпоинтов создания адреса/загрузки фото и не входят в текущую функцию.
  Интерфейс MUST NOT обещать работающую отправку нового фото или ручного адреса.
- Автосохранение инструкций из подписи макета означает сохранение локального
  черновика в сеансе: серверного endpoint обновления черновика нет.

### Service Contract and Error Rules

#### Справочник, поиск и данные остановки

- `GET /v1/stops` принимает page (с 1), page_size (по умолчанию 10, максимум 50),
  q и необязательный zone из center/south/north/east. Фильтр зон не добавляется в UI.
  Ответ 200: `{items, page, page_size, total, total_pages, has_more}`; items —
  массив остановок или null при поиске без совпадений. Обзор без результатов дает [].
- Клиент использует page_size=50: все 24 точки текущего сервера помещаются в первую
  страницу. Последующие страницы проверяются до пустого items/отсутствия новых id.
  total завышен на 1, total_pages округлен вниз, has_more может оставаться true
  на пустой странице. При размере 10 страница 2 дублирует последнюю точку страницы 1
  и пропускает исходный элемент с индексом 19: такой способ не дает полный справочник.
- q обрезается по краям. Имя и адрес сопоставляются через регистрозависимое
  вхождение; телефон — по цифрам без форматирования, только если в q есть минимум
  три цифры. Клиент не обещает регистронезависимый поиск и не подменяет его локальным.
- `GET /v1/stops/{id}` возвращает объект остановки либо 404 `{error:"not_found"}`;
  повторная загрузка каждой точки не обязательна, если данные уже есть в справочнике.
- packages_max нормализуется из числа/числовой строки; null не превращается в 0.
  Сам POST создания не проверяет этот максимум, поэтому ограничение обеспечивает клиент.
  last_delivery_at приходит как ISO с Z, ISO без Z или Unix-секунды. Поле не обязано
  отображаться; если отображается, Unix-секунды не трактуются как миллисекунды,
  а строка без зоны не выдается за однозначный момент UTC. notes может отсутствовать
  или быть null. Необязательные поля не блокируют отображение/создание маршрута.

#### Фотографии прошлой доставки

- `GET /v1/stops/{id}/photos` возвращает 200 `{items:[{id,url,tag,width,height}]}`
  после задержки 3.5–4.5 секунды; возможны пустой массив и url=null.
  Теги entrance, parking, back_door отображаются как Entrance, Parking, Back door.
  Неизвестная точка дает 404 `{error:"not_found"}`. Сбой отдельной фотографии
  не считается сбоем создания маршрута.

#### Создание и уведомления

- `POST /v1/routes`: JSON `{stops:[{stop_id,packages,instructions}]}`.
  Ответ 201: `{id,stops:[{stop_id,packages,instructions}],status:"draft"}`.
  Клиент сохраняет id и проверяет возвращенный состав и текст перед уведомлениями;
  расхождение не объявляется полным успехом и не вызывает повторный POST создания.
- Сервер приводит packages через Number(value) || 1 и instructions к строке,
  затем молча обрезает текст через slice(0,200). API.md и макет обещают 250,
  но клиент MUST ограничивать ввод 200 единицами UTF-16 и показывать N/200.
  Обязательность непустой инструкции, уникальность stop_id, целые положительные
  количества и соответствие packages_max проверяет клиент: сервер это не гарантирует.
- Создание возвращает 400 `{error:"malformed_json"}` при невалидном JSON и
  422 `{error:"validation_failed",fields:{stops:"required"}}` при отсутствии
  непустого массива stops. Такие ответы требуют исправления, а не слепого повтора.
- `POST /v1/routes/{id}/notify`: JSON `{stop_id}` и заголовок Idempotency-Key.
  HTTP 200 может содержать `{stop_id,status:"failed",reason:"carrier_rejected",attempts}`
  либо `{stop_id,status:"sent",sent_at,attempts,deliveries}`. Проверка только HTTP-кода
  недостаточна. Первый вызов для каждой третьей точки (индекс % 3 = 2) дает failed,
  следующая новая попытка дает sent.
- Реестр идемпотентности уведомления привязан к routeId + stopId + ключу и сохраняет
  в том числе failed. После подтвержденного failed нужен новый ключ; при неизвестном
  исходе сохраняется старый. Сервер записывает результат после задержки 0.6–1.5 секунды
  и не блокирует конкурентные дубли: клиент сериализует попытки одной точки.
- Уведомления возвращают 404 `{error:"route_not_found"}` для неизвестного маршрута
  и 422 `{error:"validation_failed",fields:{stop_id:"required"}}` без stop_id.
  Ошибка относится к созданному маршруту/точке; автоматическое пересоздание запрещено.
- У POST /v1/routes нет поддержки Idempotency-Key и нет endpoint чтения созданного
  маршрута для сверки. Потеря ответа создания оставляет неизвестный результат;
  клиент не делает автоматический повтор и предупреждает о риске дубля при ручном.
  Перезапуск mock-сервера очищает маршруты и реестр уведомлений.

#### Общие ошибки и повторные попытки

- После 30 запросов в минутном окне на IP сервер возвращает 429
  `{error:"rate_limited"}` и Retry-After в секундах. Поиск, страницы, фото
  и уведомления делят лимит; непрерывные/бесконечные повторы запрещены.
- Все запросы, кроме OPTIONS, увеличивают общий seq, включая health и ошибки.
  В обработчике списка при seq % 9 = 0 возвращается 500
  `{error:"internal_error",request_id}`; иначе при seq % 14 = 0 — медленный
  503 `{error:"upstream_unavailable"}` с Retry-After: 2. Это не отдельный счетчик
  запросов списка; при совпадении условий первым срабатывает 500.
- GET после 500/сбоя связи допускает Retry; 503/429 повторяются не раньше Retry-After.
  Черновик и уже загруженные данные сохраняются. Отказы не маскируются пустым списком.
- Общий обработчик может вернуть 500 `{error:"internal_error",detail}`;
  неизвестный endpoint — 404 `{error:"no_such_route",path}`. Пользователю показывается
  английская ошибка, диагностические поля сохраняются для разбора без вывода raw JSON в UI.
- `GET /health` возвращает `{ok:true,requests:N}` для проверки доступности;
  это не подтверждение сохранения маршрута или отправки уведомления.
