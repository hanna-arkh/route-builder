# Quickstart validation: Route Builder core / iOS

Это руководство для реализации и последующей приемки. На этапе планирования
экраны не написаны: приведенные сценарии не объявляются выполненными.

## 1. Предварительные условия

- Node >=22.13.x для Expo SDK58, npm и зависимости из package-lock.json.
- iPhone с iOS и Expo Go, совместимыми с SDK58; устройство, версия ОС и runtime
  фиксируются в отчете. Portrait. При использовании симулятора это явно отмечается.
- Сервис server.js и компьютер в одной доступной сети с устройством.
- Единственная точка baseUrl после реализации: src/config/api.ts.
  Физический iPhone: http://<LAN-IP-компьютера>:4000; iOS Simulator: http://localhost:4000.
  Адрес API не является URL Metro: подключение к Metro не доказывает доступ к API.

## 2. Подготовка и запуск

Из корня репозитория, установка уже зафиксированных зависимостей:

```bash
npm ci
```

В foundation-фазе реализации, а не при генерации этих документов:

```bash
npx expo install react-native-safe-area-context
npx expo lint
```

Второй вызов может предложить установить/настроить ESLint: завершить настройку
осознанно и проверить изменения package.json, lock и flat config. Не считать
выход без конфигурации пройденной проверкой. Другие runtime-библиотеки не нужны.

Терминал 1:

```bash
node server.js
```

Терминал 2, сначала для проверки starter до реализации экранов, затем для приложения:

```bash
npx expo start
```

Открыть проект через Expo Go на iPhone. Для симулятора с установленной средой
использовать iOS-действие CLI. Проверить отдельно доступ к локальному HTTP:
на устройстве localhost не адрес компьютера. Не менять сервер для обхода проблем.
При блокировке HTTP выбранным runtime настроить только требуемое debug-исключение
через Expo config и повторно проверить runtime по официальной документации SDK58.

### 2.1. Обязательный runtime/HTTP gate до T015

В T014, до написания экранов, открыть существующий starter на целевой iOS.
Временно смонтировать RouteBuilderProvider в App.tsx и вывести число полученных
точек через его loadStops; сетевой вызов остается в src/api/, не в UI.
Запрос идет на baseUrl из src/config/api.ts. Критерий прохода: приложение работает
в выбранном runtime и получает 24 уникальные точки по HTTP, без необработанной ошибки.
Safari/curl на компьютере не заменяют запрос из iOS-приложения.

Записать модель устройства/симулятора, версию iOS/Expo Go, baseUrl и фактический
результат в verification.md. При отказе остановиться до T015: исправить адрес,
доступность сети или необходимую Expo debug-конфигурацию, затем повторить gate.
Не менять сервер и не создавать ios/ вручную. Диагностический вывод удалить в T023;
T039 только переносит проверенные шаги в README.md.

## 3. Contract smoke неизмененного сервера

Исполнять отдельно от приложения, на свежем сервере, чтобы счетчик запросов
и rate limit не смешивались с приемкой UI. Базовый адрес команд — компьютер.

```bash
curl -i 'http://localhost:4000/v1/stops?page=1&page_size=50'
curl -i 'http://localhost:4000/v1/stops?page=1&page_size=50&q=North%20Cafe'
curl -i 'http://localhost:4000/v1/stops?page=1&page_size=50&q=zzzzzz'
curl -i -X POST 'http://localhost:4000/v1/routes' -H 'Content-Type: application/json' --data '{'
curl -i -X POST 'http://localhost:4000/v1/routes' -H 'Content-Type: application/json' --data '{"stops":[]}'
curl -i -X POST 'http://localhost:4000/v1/routes' -H 'Content-Type: application/json' --data '{"stops":[{"stop_id":"stp_1001","packages":2,"instructions":"Use the main entrance"}]}'
```

Ожидается: 24 уникальных id; отдельная выдача North Cafe; items=null для пустого
поиска; 400 с error=malformed_json для незавершенного JSON `{`; 422 с
fields.stops для пустого массива; 201 с id/stops/status=draft для корректного POST.
Неверные total/total_pages/has_more не исправляются на сервере.
Этот smoke создает один маршрут: начать UI-приемку с отдельного свежего запуска,
если требуется однозначно считать число созданий.

Для ошибок списка остановить и снова запустить сервер, затем в Bash/Zsh:

```bash
for request in {1..14}; do curl -s -o /private/tmp/route-builder-response.json -w "$request %{http_code}\n" 'http://localhost:4000/v1/stops?page=1&page_size=50'; done
```

Без других запросов девятый даст 500, четырнадцатый — 503. Повторный curl -i на
соответствующем номере позволяет увидеть тело и Retry-After: 2. Для 429 на свежем
сервере выполнить 31 последовательный запрос в пределах минуты, последний
с -i: увидеть Retry-After и прекратить запросы до его истечения.
Полный формат и классификация: [contracts/api.md](contracts/api.md).

## 4. Приемка UI на iOS

1. Полный список: 24 уникальные точки, правильные секции, 24/7 Pharmacy в #,
   длинное имя не ломает строку; английский LTR.
2. One stop → выбрать другую точку; Multi-stop → три разных точки; повторный
   выбор снимает точку. Чипы, N stops и сумма посылок, если есть, согласованы.
3. Пилюля N×: − не уходит ниже 1, + соблюдает числовой/строковый packages_max;
   null не означает 0. Save сохраняет, закрытие без Save — нет.
4. Поиск North Cafe, затем отсутствие совпадений; очистка восстанавливает кеш.
   Быстрая смена текста и задержка ответов не показывают старую выдачу.
5. Continue: карточки в порядке выбора, текст сохраняется при Back. Clear all
   очищает свою карточку, Remove from route удаляет только нужную точку.
   Последняя удалена → Stops, Continue недоступна.
6. Пустая инструкция и пробелы в каждой из трех позиций блокируют POST;
   подсвечены все ошибки. Исправить, проверить 200/201 и emoji на границе N/200.
7. На iPhone с открытой клавиатурой активное поле/ошибка/footer доступны,
   нижняя панель учитывает safe area, действия достигаются одной рукой.
8. Уже перед T024 проверить все sending-блокировки T022/T023: Back, изменение
   текста/выбора/количества, Remove, Clear all, Submit, New route; проверить также
   запрет действий через Context. T034 повторяет эту проверку после расширения UI.
   На корректном черновике десять быстрых нажатий Finish instructions до ответа:
   только один POST в development Network inspector, индикатор виден;
   редактирование/Back недоступны. Повторить 20 прогонов с New route между ними.
9. Правильный 201 → Route created и id. Повтор отправки недоступен;
   New route дает пустой черновик, не повторяет предыдущий POST.
10. Выключить сеть/остановить сервер перед отправкой: через <=10 секунд ошибка,
    данные сохранены, нет автоматического POST; ручной повтор требует предупреждения
    о возможном дубле. Восстановить сеть и подтвердить только осознанный Retry.
11. Проверить 429/503, поздние/поврежденные ответы и неизвестный результат через
    выбранный временный Node-прокси по §4.1. Network inspector используется для
    наблюдения запросов, а не как неподтвержденный инструмент подмены ответов.

### 4.1. Воспроизводимый ручной стенд для T041

Во время T041 создать `/private/tmp/route-builder-fault-proxy.cjs` на встроенных
модулях Node, без npm-зависимостей. Это временный инструмент ручной проверки,
не код приложения, не изменение server.js и не автоматический тестовый framework.
Исходник стенда приложить к доказательствам проверки или сохранить его точную
копию/хеш с отчетом, чтобы следующий проверяющий мог повторить сценарии.

Контракт запуска: `--mode` обязателен, upstream фиксирован на localhost:4000,
входящий порт 4001 на сетевом интерфейсе компьютера. Перезапуск сбрасывает счетчики
режима. Все не затронутые сценарием запросы передаются upstream без изменений.
Режимы ошибок срабатывают на первый подходящий запрос за запуск, затем идет passthrough.
Приложение получает только штатные GET /v1/stops и POST /v1/routes; служебные
endpoint в клиент или сервер не добавляются. Логировать только номер запроса,
метод, pathname без q, время/код, количество POST и примененный режим — без контактов
и тел с инструкциями. Контролируемые ответы явно маркировать в отчете как подмененные.

| Режим | Точное действие стенда | Действия и ожидаемый результат UI |
|---|---|---|
| reorder | Для q=North сохранить реальный ответ upstream и задержать выдачу на 1500 мс; для q=North Cafe выдать ответ без дополнительной задержки. Применять к каждой из этих двух выдач, а не только первой | Ввести North, ждать 500 мс, заменить на North Cafe. Последняя выдача остается на экране после завершения старой; отмена старого запроса тоже допустима и фиксируется |
| rate-limit | Первый GET вернуть 429, JSON {"error":"rate_limited"}, Retry-After: 3, без upstream | Retry и новый q не вызывают запрос до трех секунд; затем только явный Retry; выбор сохранен |
| unavailable | Первый GET вернуть 503, JSON {"error":"upstream_unavailable"}, Retry-After: 2, без upstream | Ошибка отличается от empty; раннего запроса нет, после ожидания ручной Retry получает данные |
| malformed | Первый GET вернуть HTTP 200 с Content-Type application/json и телом `{` | Показана ошибка формата, а не пустой результат; черновик сохранен, ручной Retry восстанавливает список |
| mismatch | Первый POST передать upstream; в его 201 изменить instructions первой точки добавлением `!`, сохранив id и status | Успех не показывается; исходный текст и известный id сохранены, автоматического второго POST нет |
| slow-create | Каждый POST передать upstream один раз и задержать передачу ответа на 1500 мс | Десять быстрых нажатий до ответа дают один входящий и один upstream POST; повторить 20 прогонов с New route |
| lost-create | Первый POST передать upstream; после получения 201 задержать выдачу ответа клиенту на 12000 мс | Клиент завершает ожидание по таймауту 10 секунд, хранит черновик и предупреждает о неизвестном результате; без подтверждения второго POST нет |

Стенд обрабатывает тела/заголовки как прокси и закрывает upstream-подключения при
остановке процесса. Для reorder сначала получить оба реальных ответа, проверить их
200 и фактический порядок выдачи; отмененный клиентом запрос отметить отдельно,
не выдавая его за полученный поздний ответ. Для slow-create отсутствие ошибки 429
проверять явно: начать с чистого сервера, не выполнять лишние поиски между прогонами.

После подготовки стенда запуск воспроизводится командами:

```bash
node server.js
```

В другом терминале (по одному режиму за запуск):

```bash
node /private/tmp/route-builder-fault-proxy.cjs --mode reorder
```

Временно поменять только baseUrl в src/config/api.ts: iPhone —
http://<LAN-IP-компьютера>:4001, симулятор — http://localhost:4001; перезагрузить
приложение. Для режима ошибки GET она срабатывает при первой загрузке; подготовить
выбор, получить исходные данные, затем перезапустить прокси нужным режимом и
инициировать новый поиск, если нужно проверить сохранение уже заполненного черновика.
Для POST-режимов заполнить корректный черновик до нажатия Finish instructions.
Перед следующим режимом остановить прокси, запустить с другим --mode и сбросить
состояние приложения. По завершении вернуть baseUrl на порт 4000 и остановить стенд.

Записать режим, действия, метки времени, счетчики входящих/upstream POST и наблюдаемый
результат в verification.md. Проверки настоящего server.js из §3 выполнять напрямую
на 4000: подмененные ответы не подтверждают его контракт. Пока стенд не подготовлен
или сценарий не воспроизведен, соответствующий пункт остается непроверенным.
